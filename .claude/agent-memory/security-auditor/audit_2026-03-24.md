## Post-Remediation Audit — 2026-03-24

**Scope**: All contracts in src/core/, src/spoke/, src/core/centuari/, src/core/pcbt/ (36 files).

**Previous audit**: 2026-03-23 found 8 CRITICAL, 12 HIGH, 13 MEDIUM (note: summary file says 5C/9H/12M but actual was higher).

**Fix verification**: 15 of 16 prior fixes verified correct. H-06 (YieldRouter verifyReserveRatio) partially fixed — per-deployment check works but aggregate view function still returns true unconditionally.

### Findings Summary

**CRITICAL (3)**:
1. SpokeVaultRWA.releaseLiquidation() — onlyLayerZeroFromHub modifier missing srcEid and sender checks. Any LZ message from any chain can drain all locked RWAs. C-08 fix only applied to lzReceive(), not releaseLiquidation().
2. SpokePayout.release() — permissionless, caller-supplied user/asset/amount not validated against stored QueuedWithdrawal. Total drain of spoke vault.
3. PCBTVault withdrawal queue — shares not locked at request time. Transferring shares blocks entire queue at maturity processing.

**HIGH (4)**:
1. LiquidationEngine.liquidate() — no ERC20 token transfers. Accounting-only liquidation.
2. RiskModule._getWeightedCollateralUSD() — uses stale usdValueCached, not fresh oracle.
3. CentuariEndpoint._processLiquidations() line 305 — credits debtRepaid to borrower (creates value from nothing).
4. YieldRouter.verifyReserveRatio() — returns true unconditionally (H-06 incomplete fix).

**MEDIUM (8)**: WithdrawalRegistry no fund locking, CollateralRegistry no staleness on refresh, CentuariEndpoint admin setters no timelock, AssetBehaviorRegistry instant first update, FeeController ordering assumption, no debt ceiling/minBorrow in settlement, PCBTVault admin no timelock, CentuariRouter ERC-4626 stubs misleading.

### Recurring Patterns
- **Incomplete fix propagation**: Fix applied to one code path but not all paths with same vulnerability (SpokeVaultRWA lzReceive fixed, releaseLiquidation not)
- **Accounting without token transfer**: LiquidationEngine, CentuariBondERC20 redeem — accounting logic complete, actual ERC20 movement missing
- **Request queues without escrow**: PCBTVault withdrawal queue, WithdrawalRegistry — requests recorded but assets not locked
- **Missing timelocks on admin setters**: CentuariEndpoint, PCBTVault, SpokeVaultRWA critical config setters
- **Stale cached oracle values in HF**: Known issue persisting from initial review

**Why:** These patterns recur because: (1) multi-path functions get partially fixed, (2) accounting is implemented before transfer logic and the transfer is deferred then forgotten, (3) queue patterns default to "record request" without considering the asset custody gap.

**How to apply:** On every future review, explicitly check: does every code path to the same resource have the same protection? Does every accounting change have a corresponding token movement? Does every queue/request lock the subject asset?
